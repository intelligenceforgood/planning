## Risks

| Risk                                                                                                                     | Impact                                | Mitigation                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shadow mode doubles memory: loading two models (Gemma 2B ~5GB + XGBoost) in one Cloud Run instance (n1-standard-4, 15GB) | OOM under concurrent requests         | XGBoost shadow + XGBoost champion is fine (~100MB each). If shadowing a PyTorch model against XGBoost, bump machine to n1-standard-8 or run shadow in a separate Cloud Run revision |
| Vizier runs the pipeline N times with different params — costs N × training cost per trial                               | Budget overrun at 15 trials × GPU     | Cap at 10 trials for GPU sweeps, 20 for CPU (XGBoost). Vizier Bayesian optimization converges faster than random search. Budget ceiling: $50/sweep                                  |
| Vertex AI Model Monitoring on low-traffic endpoint (~0.2 QPS)                                                            | False drift alerts on sparse sample   | Start with `prediction_sampling_rate = 1.0`; set drift threshold at 2σ instead of 1σ; tune after 2 weeks of baseline data                                                           |
| NER subword tokenizer alignment: BIO tags must be expanded to match subword tokens, then collapsed at prediction         | Silent label corruption if misaligned | Implement `align_labels_with_tokens()` utility with explicit unit tests on edge cases (multi-character entities, adjacent entities, single-token entities)                          |
| Continuous retraining trigger fires on LLM-bootstrap labels                                                              | Wasted training on low-quality labels | Gate: `evaluate_retraining_conditions` must filter `label_source = 'analyst'` only; require ≥ 200 analyst labels, not total labels                                                  |
| NER model selection: `bert-base-uncased` lacks domain knowledge for fraud entity types (crypto wallets, case references) | Low recall on domain entities         | Start with `dslim/bert-base-NER` (pre-trained NER) or `microsoft/deberta-v3-base` (stronger on diverse text). Benchmark against few-shot LLM extraction before committing a model.  |

### 2.2 — Vertex AI Vizier hyperparameter tuning

Vizier operates OUTSIDE the KFP pipeline. It manages a study that spawns multiple pipeline runs with different hyperparameters, evaluates their results, and selects the best config. This is different from adding a step inside the pipeline.

- [ ] Implement `training/vizier.py`:

  - `run_vizier_sweep(study_name, training_pipeline_fn, base_config)`:

## Sprint 3 — Continuous Retraining Pipeline

**Goal:** Close the continuous learning loop — trigger conditions are evaluated daily, and when met, the training pipeline fires automatically. Best model promotes through eval gate.
**Exit criteria:** Cloud Scheduler triggers daily evaluation. When conditions are met, pipeline submits automatically. E2E validated on dev with synthetic data.

- [ ] Extend `scripts/submit_pipeline.py` (already exists — submits pipeline to Vertex AI):
  - Add `submit_pipeline(config_path, pipeline_yaml_path, experiment_name, trigger_reason) -> str`:
    - Compiles KFP pipeline YAML if stale (source `.py` newer than compiled `.yaml`)
    - Creates `aiplatform.PipelineJob` with parameters from config YAML

    - Returns pipeline job resource name
  - This function is called by both manual runs AND the automated trigger (3.2)
- [ ] Unit tests: mock `aiplatform.PipelineJob`, assert parameter passing, assert tag metadata

### 3.2 — Retraining trigger Cloud Run Job

- [ ] Create `scripts/trigger_retraining.py` (Cloud Run Job entry point):
  - Accepts args: `--capability` (default: `classification`), `--force` (boolean flag)
  - Calls `evaluate_retraining_conditions(capability, force=args.force)` from `triggers.py`
  - If `should_retrain`:
    - Calls `submit_pipeline()` with the capability's default config
    - Records trigger event with `pipeline_job_name` in `analytics_trigger_log`
    - Logs structured JSON: `{"action": "retrain_submitted", "capability": ..., "reasons": ..., "pipeline_job": ...}`

  - **Exit code 0 always** (Cloud Run Jobs treat exit code 1 as failure). Use structured logging for alerting, not exit codes.

  - Add Cloud Scheduler: daily at 6 AM UTC → invokes `retrain-trigger --capability classification`
  - Add Cloud Scheduler: monthly (1st of month, 7 AM UTC) → invokes `retrain-trigger --capability classification --force`
- [ ] Makefile: add `trigger-retrain-dev` target
- [ ] Unit tests: mock `evaluate_retraining_conditions`, mock `submit_pipeline`, assert both branches (retrain vs. skip)
